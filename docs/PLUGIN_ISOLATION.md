# 插件隔离方案（发布版为何不加载插件）

> 状态：**未实现**。本文是 1.0 的决策文档 + 1.1 的施工蓝图。它回答两个问题：
> 为什么发布版现在**不加载**插件，以及要让插件真正可用需要做什么。

## 1. 现状（一句话）

插件的**治理**已经完整、有测试；插件的**执行**在发布版被主动跳过。

- 治理（已实现、已有测试）：清单解析、摘要（digest）比对、签名校验、信任源、撤销/版本策略/回滚、
  激活前逐项同意、崩溃隔离与配额、`.nekowite/vault-plugin-audit.log` 审计、`ai` 权限、以及
  写入策略（`pluginEditorGuard`：插件往文档里写要过用户权限）。
- 执行（发布版跳过）：`apps/desktop/src/services/plugins.ts` 的 `isPluginImportAllowedByCsp()`
  在检测到 Tauri 运行时后返回 `false`，`loadVaultPlugins` 直接返回，只弹一次「插件功能因安全策略不可用」。

## 2. 为什么跳过：插件代码与主程序同权限

宿主用 `import(/* @vite-ignore */ specifier)`（`packages/plugin-host/src/loader.ts:112`）把插件模块
加载进**主窗口**，并在同一上下文里调用插件回调。于是插件代码可以：

1. 读写应用能读写的任何文件（vault 里的全部笔记，包括用户没打开的）；
2. 访问 DOM，读取屏幕上的一切（含正在编辑的正文）；
3. 发起网络请求，把上面两样发出去；
4. 调用 `ctx.ai`（在声明了 `ai` 时）消耗用户的密钥与额度。

加载入口是 `blob:` 模块导入，而发布版 CSP 是 `script-src 'self' 'wasm-unsafe-eval'`（`tauri.conf.json`），
`blob:` 被禁止——这正是当前的执行闸门。它在**打包版**成立、在浏览器 Demo/单测里不成立，
所以治理代码在开发环境下仍然被完整走到。

关键点：**同意对话框让用户批准的是一个摘要，不是一份可审计的能力清单**。用户批准「运行这个插件」在
语义上等于「让这段代码拥有我的全部权限」——这正是发布版选择不加载的原因，而不是疏忽。

## 3. 三条可选路线

### A. 维持现状：1.0 不提供插件（推荐给 1.0）

- 代价：零。已实现的能力不删，等隔离落地后自动可用。
- 要求：所有面向用户的入口必须**如实说明**（设置 → 插件里已加提示；`docs/PLUGIN_SDK.md` 需同样说明）。
- 风险：把「插件」写进 1.0 的功能列表却不说明不可用，等于虚假宣传——CHANGELOG 与 README 必须写明。

### B. 直接放开（改 CSP 允许 `blob:`）

- 代价：一行 CSP + 更新若干测试。
- 收益：插件立刻可用，与 Obsidian/VS Code 生态的惯例一致（它们的插件同样拥有完整权限）。
- 风险：此后任何**改过的**插件（摘要会拦一次，用户点过「重新批准」之后就没拦的了）或**新装的**恶意插件，
  一旦装上就是完全接管。治理只能告诉你「代码变了」，不能告诉你「代码变坏了」。
- 若选这条，必须同时做：同意对话框写明「拥有与 NekoWite 相同的权限，可读写你的知识库并发起网络请求」；
  `docs/SECURITY.md` 把插件从「已禁用」改为「受信任代码」并给出威胁模型；README 给出警告。

### C. 沙箱 iframe + RPC（推荐给 1.1）

把插件代码放进 `<iframe sandbox="allow-scripts">`（唯一不透明源，拿不到父文档 DOM、storage、cookie），
宿主与插件之间只走 `postMessage`。插件**不再**直接拿到编辑器对象，而是拿到一层 RPC 代理。

| 能力 | 隔离后如何实现 | 是否仍需用户同意 |
| --- | --- | --- |
| 插入/替换文档 | RPC → 应用侧已有的 `pluginEditorGuard`（**已经是权限闸门**） | 是（现有策略） |
| 读取文档 | RPC → 应用侧只返回当前文档（或选区），不返回整个 vault | 是（新增：授予后按次/按会话） |
| `ctx.ai.complete` | RPC → 应用侧 `completeForPlugin`（已有 60s 上限与空答拒绝） | 是（现有 `ai` 权限） |
| 读写其他文件 | RPC → 应用侧按**路径白名单**（vault 内、且限定子目录） | 是（现有 `fs` 权限） |
| 网络 | 默认**不提供**：iframe 内 CSP `connect-src 'none'`；确有需要再走应用侧代理 + 域名白名单 | 是（`network`） |
| 命令 / 工具栏 | 插件注册的是**声明**（id、标题、图标）；点击时宿主把 `run(id)` 发给沙箱 | 否 |
| 生命周期钩子 | 宿主把事件（保存前/后、打开文档）发给沙箱，返回值为可选的 RPC 调用 | 否 |

**能力缺口（必须如实说明）**：`components`（插件提供的 Vue 组件）**无法**在隔离模型下工作——
组件需要挂到应用自己的 DOM 树里渲染。隔离版要么不支持自定义组件（只保留命令/工具栏/生命周期），
要么把插件 UI 限制为「沙箱内的面板」（iframe 挂在侧栏，不进入正文）。这是产品取舍，不是实现细节。

施工清单（C 路线）：

1. `packages/plugin-host`：新增 `sandbox.ts`（iframe 创建、srcdoc、CSP、握手、消息校验）与
   `rpc.ts`（请求/响应、id 配对、超时、结构化克隆白名单）；把 `runtime.ts` 的调用点从「直接调用函数」
   改为「发送 RPC」，并保留现有 `markPluginUnstable` 配额/超时语义。
2. 消息协议：`{ v: 1, id, kind: 'call' | 'result' | 'event', method, params, error }`；**所有** `params`
   必须显式校验（插件是敌意输入），拒绝未知 `method`，限制消息大小。
3. 应用侧：把 `pluginEditorGuard` / `completeForPlugin` 接到 RPC 上（两者已存在，只需接线）；
   为「读文档」新增一个权限种类（`aiPermissions.ts` 的 `AiWriteKind` 之外新增读类别）。
4. 治理：`import-refused` 的审计事件改为沙箱握手失败；同意对话框改为列出**实际会经过 RPC 的能力**
   （这才是可审计的清单）。
5. 测试：沙箱逃逸用例（尝试 `parent.document`、`localStorage`、`fetch` 必须失败）；未知 method、
   超大消息、握手超时、插件在 RPC 中途卸载；应用侧每个 RPC 处理函数的权限用例。
6. 文档：`docs/PLUGIN_SDK.md` 增加隔离版约束（无自定义组件、网络默认关闭）；`docs/SECURITY.md` 更新威胁模型。

## 4. 决策所需

1. 选 A、B 还是 C（这不是工程判断，是产品/风险偏好）。
2. 若选 B：接受「插件 = 完全信任的代码」，并同意在同意对话框与文档里把这句话写清楚。
3. 若选 C：接受「1.0 没有插件」，并接受隔离版**不支持插件自定义 UI 组件**。

未选 C 之前，本文列出的执行闸门保持不变：**发布版不加载插件代码**。
